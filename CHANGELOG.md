# Changelog

All notable changes to Lager are listed here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and Lager follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html). While the version is 0.x, a minor release may contain breaking changes.

## [Unreleased]

### Added

- **Show password:** every password field on the platform (sign-in, create account, new password after a reset, change password, the password confirmations of two-step sign-in) has a button with an eye that shows what was typed and hides it again. It works by mouse, touch and keyboard and is 44 px. Before the form is sent the field is a password field again, so browsers still offer to save it. The API-key and SMTP-password fields of the administration area, which are pasted, have none; without script nothing changes (#92).
- **Apps open without a connection:** every app that was opened once opens again offline, also from the home screen, without any work in the app. The runtime registers a service worker (`/__lager/sw.js`) that keeps the page, the viewer's session, the runtime and the scripts, stylesheets and fonts the page loads from CDNs, and answers with them when the network fails, the server is down or does not answer within 4 seconds. Offline, `lager.use("db")` and `lager.use("user")` resolve with the last known viewer instead of `null` (the kept session never holds the email address, so `user.email()` resolves `null` offline); reads and writes still need the server (`onSnapshot` catches up once the connection is back, the other calls reject with `unavailable`). Only the top-level page is answered from the copy, never a frame. The server marks what may be kept (`X-Lager-Offline: 1`), and the worker deletes everything as soon as an answer online says the viewer has no access any more or the instance is gone. Apps whose data would mislead when it is not current declare `{"db": {"offline": false}}`; the runtime then removes the worker. This is the first of three steps: keeping data for reading offline and queueing writes follow. See [ADR 0020](docs/adr/0020-offline-first-runtime.md) and [Opening without a connection](docs/building-apps.md#opening-without-a-connection).
- **Mail server in the administration area:** administrators set up outgoing mail under Administration → Mail (SMTP host, TLS, STARTTLS or none required, port, user name, password and sender) instead of editing `LAGER_SMTP_URL` and restarting, so confirmation mails at registration, password resets and invitations go out. The password is stored encrypted with a key derived from `LAGER_SECRET` and is removed when the host, port, encryption or user name changes, so it never goes to a server it was not entered for. **Send a test mail** shows what the mail server answered, and changes apply to the next mail without a restart. `LAGER_SMTP_URL` still works and takes precedence. Saving a mail server stores the registration mode in effect, so registration never opens by itself. No schema change.
- **Reading large apps in parts:** the MCP tool `get_version` takes `offset` and `limit` (in bytes) and reports `offset` and `nextOffset`, so an assistant whose client caps tool results can read an app of any size over MCP alone, without an API token. A part never splits a character, a `limit` below 1024 bytes counts as 1024, and without `limit` the tool returns the whole HTML as before. The answer now also carries the version's `sha256`; assistants continue a read with the `version` of the first part, so parts never mix two versions when someone deploys meanwhile.
- **Changing an app without resending it:** the MCP tool `edit_version {slug, base_version, edits: [{old_text, new_text}], note?, capabilities?}` replaces pieces of text in the latest deployed version and deploys the result as a new version, keeping its capabilities unless new ones are given. Each `old_text` must occur exactly once, the edits apply in order, and a failed edit deploys nothing. If `base_version` is no longer the latest deployed version, the answer is `conflict`. For assistants that change a large app over several conversations: they no longer send the whole file again, and they no longer retype it, which is where small mistakes slipped in.
- **Websites named per instance:** an ingest endpoint can declare `managedOrigins: true`. The people who manage each instance then add the websites whose pages may send, on the instance page under "Data from outside" or from the app with `ingest.setOrigins(name, origins)`, without a redeploy. For apps where every owner brings their own website, such as a blog analytics dashboard; until now they needed a token endpoint with `["*"]`, whose token sits in every visitor's page source. `ingest.endpoints()` also reports `managedOrigins`, `instanceOrigins` and `canManage`; the added websites, like the token, are shown only to the people who manage the instance. The platform database moves to schema version 4 (one new column).
- **Showing an app on other websites:** an app can declare `embed` (`{"embed": {}}`, no fields), and the people who manage each instance add the websites outside Lager that may show it in a frame, on the instance page under "Shown on other websites". The instance page then answers with `frame-ancestors 'self' <websites>` instead of `'self'` alone; `X-Frame-Options: SAMEORIGIN` stays for browsers that know only that. For comment boxes, polls and forms on a blog. Addresses this Lager serves (other instances, the apps domain, custom domains, the platform) and websites on the same domain as the server can never be named, so instances still cannot frame each other; on another site the browser passes no sign-in into the frame, so the instance only ever sees a guest there. `lager.use("embed")` lets the app read the list, remove websites and link to the instance page (`manageUrl`), but not add any. At most 20 websites per instance. The platform database moves to schema version 5 (one new table). See [ADR 0018](docs/adr/0018-embedding-on-other-websites.md).
- **Storage per group and per app:** administrators can give the instances of one app, or the instances owned by the members of one group, more or less storage than `LAGER_INSTANCE_QUOTA_MB`: in the administration area on the group's page and next to each app under Apps (in MiB, 1 MiB to 1 TiB; empty follows the default again). The app's setting comes first; of several groups of the owner the largest applies. Uploads, documents and saved pages follow the storage that applies to the instance; snapshots may take 3 times it, but never less than 3 times the default. The instance page and the apps overview show it, the overview also whether it was set for the app or by which group. The platform database moves to schema version 7 (two new columns and an index). See [Limits](docs/limits.md#storage-per-group-and-per-app) (#71).

### Changed

- **A form on its way shows it:** the pressed button shows a small spinner (a still "…" when the system asks for less motion) until the next page arrives, and pressing again sends nothing. A slow test mail, a test message to an AI provider or a sign-in on small hardware no longer looks like a page that hung, and is no longer sent twice. Coming back with the back button shows the button as it was (#93).
- **Two-step sign-in, scan instead of type:** the setup page shows a QR code that authenticator apps read with the camera, next to the key and the "Open in authenticator app" button, which stay. The code is made on the server and sent as an image in the page: no new dependency, no outside service, black on white in light and dark mode. Typing the 32-character key on a phone is no longer the only way when setting up on a computer (#91).
- **Empty lists say what to do next:** an empty list explains itself in one more sentence. "Yours" on the home page has buttons for the next step (Browse the catalog, and Publish for those who deploy). An instance shared with nobody says who can open it right now, given its visibility. No snapshots yet says when Lager takes one. No API tokens says what a token is for and that AI assistants need none. No collaborators says what a collaborator does. No groups says what groups are for (#90).
- **Catalog on a page of its own:** "Catalog" in the main navigation (a tab on phones) opens `/catalog` and marks itself as the current page, instead of jumping to a section at the bottom of the home page. The catalog lists the apps shared with everyone and those one can start a copy of under headings of their own. The home page keeps "Yours" and "Shared with you" and links to the catalog ("More apps on this server"); for someone with no app of their own the link is the main button. After "Create your copy" the home page shows the new copy; a name that cannot be used is reported in the catalog, at its field (#89).
- **App cards open on a tap anywhere:** on the home and publish pages a card that opens something is one target: its title is the link and covers the card, as on a home screen, while Manage and "Get your own copy" keep their own targets. Keyboard and screen readers reach each destination once (the visible Open button only repeats the title's link), the card shows the focus ring, and only cards that open something lift on hover (#88).
- **Naming a new instance:** the field for a new instance's name ("Get your own copy" on the home page, "Create instance" on the app page) is filled with a free name: the app's name with a number (`notes-2`), so getting a copy takes one press and nothing about the person ends up in the address. The rules and the address the name becomes stand under the field and follow what is typed; the browser checks the shape before sending; opening the panel puts the cursor in the field. The label is just "Name" (#86).
- **Home page in plain words:** the home page speaks of apps and copies instead of instances ("Yours", "Shared with you", "Get your own copy", "Your copy notes-2 is ready."), in one voice. Cards of apps shared with you say whose they are and at which level you have them, without the owner's "Private" badge and the version, which only those who manage an app can act on. A catalog app you already have a copy of says so, and the name under each title is plain text rather than small grey code (#85).
- **Sharing with someone new:** sharing with an address that has no account keeps the address in the field and says what to do next: an administrator is pointed to Administration › Invitations, everyone else is told to ask an administrator. People and groups are shared through two separate forms, and a post that names both is refused instead of quietly ignoring the group. The instance page has a **Copy link** button next to **Open**, and the notice after sharing offers the link to copy as well (#84).
- **Instance page, who may open it:** "Who may open the instance?" moved from Details to the top of the Sharing card, above the people and groups, so access is decided in one place, and on a phone that is the second card instead of the last. The update and badge switches share one form with one Save, so changing both keeps both, and the hint says "When this is on". The newest version carries a "latest" mark, and an instance that was rolled back while updates are on says that the next deploy moves it forward again and how to stay (#83).
- **A question before what cannot be taken back, Undo for what can:** deleting a group, an AI provider, model or AI group, revoking an API token or an invitation, replacing an endpoint's token, removing the mail server and restoring a snapshot no longer happen on one click: a dialog names what is affected and what happens, with Cancel focused (without script, or from an older page, the server asks on a page of its own). Removing a share, a group member, a collaborator, a custom domain or a website, and deactivating an account or an instance, offer **Undo** in the notice that follows (#75).
- **A word after every form:** saving, sharing, activating a version, restoring a snapshot, adding a domain, switching an endpoint, deleting an instance or app, revoking a token and every form in the administration area now end with a notice that names what changed ("Shared with jonas@example.com as Contributor.", "Anyone with the address can open notes now, without signing in.", "Version 3 is active. The data from before the change is saved as a snapshot."), in the viewer's language. On the instance, app, home and publish pages the notice stands right above the card that changed and the page scrolls there, so on a phone the result is on screen too. The names and addresses in a notice travel encrypted in the page address, so browser history and proxy logs do not show them. Until now most forms reloaded the page at the top without a word (#76).
- **Administration › Users:** the list of accounts shows name, role, AI group, status and the day each account was created, with a **Manage** link per account. Role, AI group, reset link, two-step sign-in, deactivating and deleting moved to a page of their own for each account (`/admin/users/<id>`), with a sentence on what each does. One's own account offers neither deactivating nor deleting, and the server refuses deactivating it. With a form in every cell the list no longer fit next to the navigation: on every window wider than 1100 px its last column was cut off, and the date broke into four lines (#73).
- **Docs:** the ChatGPT steps no longer ask for developer mode, which ChatGPT no longer needs for custom MCP servers, and say which plans may use connectors that write (Business, Enterprise and Edu; Pro reads only) and who may add one in a workspace.
- **Dependencies:** nodemailer 10.6.1 (upstream bug fixes; Lager's emails do not change).

### Fixed

- **Buttons that repeat say what they act on:** for screen readers and voice control, every repeated button and link now has a name of its own that starts with its visible word: "Save: Level of jonas@example.com", "Remove: notes.example.com", "Activate: v3", "Revoke: laptop", "Save: Role". On the instance page alone there were five "Save", four "HTML" and three "Activate". The version link "HTML" now reads **Download** ("Download: v3 (HTML)"), and two copies of one app on the home page are told apart by their address. A test fails on any page where two controls that do different things share a name (#94).
- **An expired reset link says so first:** opening a reset link that has expired or was used showed the "New password" form, and only after the new password was typed did it answer "Link invalid". It now says at once that the link no longer works, with a button to ask for a new one (without mail, whom to ask). Without mail, an expired reset link no longer speaks of a "confirmation link", and the page about sending a confirmation link again is titled "Confirm email address" (#82, follow-up to #74).
- **Tab bar names:** on phones the links of the tab bar carried the long label as their accessible name while showing the short one ("Admin" named "Administration", in German "Publizieren" named "Veröffentlichen"), so voice control could not find them by what they show. Each link is now named by the label on screen at either width (WCAG 2.5.3) (#81).
- **Dates in the viewer's own time:** versions, snapshots, tokens, invitations and accounts showed their times in UTC without saying so, eight hours off in Los Angeles and on the wrong day near midnight. The platform script now writes them in the viewer's time zone and the page's language; without the script (and on pages of instance hosts) they end in "UTC" (#80).
- **Long button labels on narrow phones:** a button whose label is longer than its card, such as "Anmeldung in zwei Schritten einrichten" on the German account page at 320 px, now wraps onto a second line instead of pushing out of the card and making the whole page scroll sideways. Small buttons in table rows stay on one line. No page scrolls sideways at 320 px in any of the four languages (#79).
- **A form from an out-of-date page:** instead of "That did not work. Your session has expired. Please reload the page and try again." (reloading sent the same stale form again, and the only link led home), the page now says that the form was not sent because the page was open too long or the account signed in again elsewhere, and its one button opens the page the form was on. Signing out without a session goes to the sign-in page (#78).
- **Form errors at their field:** a refused share, domain, instance name, owner, collaborator, website, token name, confirmation, group, member, invitation or storage value now comes back with the message right above the field, the field marked invalid and described by the message for screen readers, the cursor in it, and what was typed still there (never a password). On the home page the "Get your own instance" panel opens again. Until now the message was a banner at the top of the page, the input was gone and the focus was lost. A refused sign-in marks both fields and points them at its message (#87).
- **Reloading after a form:** saving the name, language or password on the account page, turning off two-step sign-in, saving or testing the mail server, testing an AI provider, turning off someone's second step and deleting an account now redirect to their page with a notice, so a reload no longer asks to send the form again (and sends no second test mail). Forms that must show a one-time secret (a new token, an invitation or reset link, recovery codes) still answer in place, and the address of every form, opened again from the address bar or a bookmark, leads to the page the form is on instead of "Not found" (#77).
- **Forgot password without mail:** on a server that sends no mail, "Forgot your password?" no longer answers "Email sent". It says that the server sends no email and to ask its administrator for a link to set a new password, and offers no form. The same goes for sending a confirmation link again, for an unconfirmed account that signs in, and for a confirmation link that no longer works (#74).

### Security

- **Two-step sign-in:** every account can turn on a second step on its account page. After the password, signing in asks for a 6-digit code from an authenticator app (TOTP, RFC 6238), or one of 10 single-use recovery codes. The right password alone gives no session, no device cookie and no way into OAuth or instances. Each code works once; wrong codes are counted per account in the database and pause the second step for 1 minute up to a day, which leaves about 5 guesses a day to someone who knows the password; the owner gets a mail when it is turned on or off, when a recovery code is used, when new recovery codes are created and when a pause starts. Turning it on signs out every other browser, disconnects AI assistants and revokes API tokens; only the browser that gave the password can see the new key and confirm it. Turning it off or creating new recovery codes needs the password and a code. Administrators can turn it off for another account (not their own) after confirming with their own password and code; that also signs the account out everywhere and revokes its API tokens. A password reset does not turn it off. The secret is encrypted with a key derived from the server secret and bound to the account; recovery codes are stored as a keyed hash. No new dependency. The platform database moves to schema version 6 (two new tables). See [Two-step sign-in](docs/users-and-sharing.md#two-step-sign-in) and [ADR 0019](docs/adr/0019-two-step-sign-in.md).

## [0.2.0] - 2026-11-20

### Added

- **Receiving data from outside:** an app can declare `ingest` endpoints, each of which appends JSON documents to one collection of an instance and can do nothing else: `POST https://<instance>/_ingest/<name>`. Pages on listed websites send without a secret (`auth: "none"`), scripts, webhooks, phone shortcuts and devices with a token (`auth: "token"`) that the instance page shows and replaces. Endpoints work on private instances, never read a cookie and store nothing about the sender; on request the server adds a daily visitor hash and the country. A data rule with `"write": "anyone"` lets guests of a public instance add documents from the page itself (an RSVP, a guestbook, a poll). What comes in is kept in a file of its own per instance (`inbox.sqlite`, not part of snapshots) with a quota of its own, `LAGER_INGEST_QUOTA_MB` (default 10 MiB per instance on top of the instance quota; `0` turns the feature off), and with limits per client address, endpoint, instance and day. The instance page has a card "Data from outside" with addresses, tokens, counters and a switch per endpoint; on an instance whose owner does not run the app, endpoints start switched off. New: `lager.use("ingest")`, the example `examples/pageviews.html`, the setting `LAGER_COUNTRY_HEADER`, and [Receiving data from outside](docs/building-apps.md#receiving-data-from-outside). The platform database moves to schema version 3 (one new table).

### Changed

- **Node.js 24 or newer** is needed to run Lager from source (it was 22.13). The Docker image and the installer already use Node 24, so they are not affected.
- **Images:** commits on `main` publish only `:edge`, without a `:sha-<commit>` tag, and earlier edge builds are deleted after each publish. Release images and their tags stay.
- **Docs:** the steps for adding Lager to claude.ai and Claude Desktop, ChatGPT and VS Code follow the current menus and configuration files of those products.
- **Database `add`:** the answer to an `add` request (`POST /__lager/db`) carries the `id` of the new document next to `doc`, also where the document itself is withheld because the writer may not read the path. In the browser runtime, `collection.add()` now sends that request and lets the server make up the id, instead of choosing one in the page and sending a `set`; apps notice no difference.
- **Activating versions:** a manager who is not the owner can no longer activate a version whose ingest endpoints differ from the active one, as was already the case for data rules.

### Security

- **Docker image:** the runtime image no longer contains `npm`, `npx`, `corepack` or `yarn`. Lager never runs them, and npm's own bundled packages (brace-expansion, undici) carried known vulnerabilities that image scanners report. For an online backup inside the container, use `node dist/backup.js` as the documentation shows; `npm run backup` works only in a source checkout.

## [0.1.0] - 2026-11-19

The first public release.

### Added

- **Deploying from your AI:** an MCP endpoint (Streamable HTTP) with OAuth 2.1 and dynamic client registration, or API tokens, through which Claude, ChatGPT, Cursor, VS Code, Gemini CLI and other MCP clients build and deploy apps; a REST API and a browser dashboard for the same tasks.
- **Apps:** single HTML files with the injected `window.lager` runtime, an own subdomain per instance, numbered versions with rollback and a note per deploy, icons, descriptions and theme colours, home-screen install, custom domains.
- **Data:** a document database per instance with live updates and access rules, file uploads, realtime rooms with presence, pages that save themselves, file downloads, snapshots before the active version changes, NDJSON export and import.
- **People and sharing:** several accounts with roles (administrator, publisher, user), invitations, open or closed registration, groups, four access levels per instance, public instances; share one instance or hand out separate instances of an app.
- **Language models:** `lager.complete()` routed to the providers you connect (Anthropic, OpenAI, OpenRouter, Mistral, Ollama or any OpenAI-compatible server), a catalog of named models, a model per app, AI groups that decide which models their people may use and how often, provider keys stored encrypted.
- **Moving apps over:** a guide served through MCP and a check tool, with which an assistant converts apps from elsewhere, such as claude.ai artifacts, to Lager.
- **Interface:** English, German, French and Spanish, in light and dark mode.
- **Operations:** a single Node.js process with SQLite and one data directory, no telemetry, an online backup command, a trash with retention, optional mail over SMTP.
- **Installation:** a one-command installer and updater for Raspberry Pi and 64-bit Linux servers, with Cloudflare Tunnel, a mode for the local network or your own reverse proxy, and a backup before every update.
- **Images:** multi-architecture Docker images (`linux/amd64`, `linux/arm64`) on the GitHub Container Registry: `:latest` and version tags for releases, `:edge` for the `main` branch.

### Upgrading from a pre-release build

An installation that ran a build from before the first release will notice these changes, the ones that need action first:

- **First start needs an administrator:** while no account exists, Lager refuses to start unless both `LAGER_ADMIN_EMAIL` and `LAGER_ADMIN_PASSWORD` are set. On such a first start, a `LAGER_SECRET` shorter than 32 characters, an administrator password shorter than 10 characters, and the example passwords from `.env.example` on an address other than this machine are refused too. Installations that already have an account are not affected, except that a short `LAGER_SECRET` logs a warning at every start.
- **Database:** the platform database is migrated to schema version 2 at the first start (a new table and a new column; nothing is removed). An older build cannot open it afterwards.
- **Stricter configuration:** `LAGER_PUBLIC_URL` must be an `http(s)` address without a path, `LAGER_APPS_DOMAIN` a bare host name, `LAGER_SMTP_URL` an `smtp(s)` address, and numbers must be whole numbers in their range. A value that is refused stops the start with one line that names the variable. `LAGER_SNAPSHOT_KEEP=0` keeps working as 1, with a warning.
- **Data directory is private:** Lager now creates directories with mode 700 and files with 600, and at the next start changes an existing data directory it owns to mode 700 (one log line says so). Scripts on the host that read the data directory as another user, for example a `cp -a` or `rsync` of a bind-mounted `./data`, need to run as the owner or with `sudo`. `node dist/backup.js` itself keeps working, but the backups it writes are now readable only by the account that ran it (directories 700, files 600): a job on the host that reads or copies them as another user must run as that account or with `sudo`.
- **Installer:** an update now stops when the backup before it fails (`LAGER_SKIP_BACKUP=1` updates without one), keeps the image it was installed with (`LAGER_IMAGE` is remembered in `installer.env`), and keeps the saved mode, domain and tunnel unless `LAGER_RECONFIGURE=1` is passed.
- **Content security policy:** platform pages now allow scripts only from Lager's own files or with a per-response nonce, and send `X-Content-Type-Options: nosniff`. A reverse proxy that injects its own inline script into the platform's pages (an analytics snippet, say) will find it blocked. The platform also answers `/robots.txt` with "disallow everything".
- **A password change revokes API tokens:** changing a password on the Account page now revokes the account's API tokens, as a reset already did. Scripts and assistants that deploy with a token need a new one afterwards. Only administrators and publishers can create API tokens, over the REST API as in the dashboard.
- **Question before the first sign-in to an app:** whoever opens an instance they neither own nor maintain is asked once whether to continue, and told that the app will see their name (and their email address, if it asks for it). People an instance was shared with are asked too. Sessions on instances that exist already keep working.
- **Confirming an email address takes the password:** the link in the confirmation mail now asks for the password chosen at registration; "Forgot your password?" confirms the address as well. With mail configured, an account created through an invitation without an address has to confirm its address like any other.
- **Accounts pause under attack:** after 10 failed sign-ins in a row an account refuses sign-ins from browsers it does not know for 30 seconds, then for up to 5 minutes. Browsers that signed in before are not affected, and "Forgot your password?" ends a pause. See [Limits on signing in and registering](docs/users-and-sharing.md#limits-on-signing-in-and-registering).
- **Hourly limits for the whole server:** 30 self-registrations, 60 confirmation mails and 60 password-reset mails per hour. The limits per client address count an IPv6 address as its /64 network. With mail configured, registering an address that already has an account answers "check your mail" and mails the owner instead of naming the address.
- **Passwords:** a password may have at most 1024 characters and is no longer cut to 300 when it is set. An account whose longer password was cut by an earlier build signs in again after a reset.
- **Snapshots are bounded by size:** all snapshots of an instance together take at most 3 times the instance quota. The next snapshot of an instance that holds more deletes the oldest ones for good, except the newest and the newest that is at least a day old. Restoring a snapshot is for the owner of the instance only, no longer for people who manage it, and restores and manual version changes are limited to 10 per instance and hour.
- **Old versions are removed:** an app keeps its newest 100 deployed versions. The next deploy of an app with more deletes the surplus for good (not to the trash), except versions an instance still runs.
- **Deploy limit:** an app takes at most 60 new versions per hour, and one person starts at most 60 new apps per hour; further deploys are refused with `deploy_rate` (HTTP 409).
- **Limits on database requests:** an instance takes at most 600 reads and 300 writes per minute from one signed-in viewer (anonymous visitors: 600 and 150 per client address, and 4800 and 1200 for all of them together); further requests get HTTP 429 with `rate_limited`, and live queries retry by themselves. A query takes at most 10 `where` clauses, 5 `orderBy` fields and 30 values in a list. An app that polls in a tight loop or builds very large queries needs changing.
- **Data rules:** writing to the private area (`data/users/<id>/…`) takes contributor level; a viewer can still read and delete there. On a path a person may write but not read, `update` and `acquire` are refused, and `set` and `add` no longer return the stored document. A refused `acquire` no longer names the holder, and an app can look up the names only of people the instance knows (its owner, the people it is shared with, authors and people in its rooms).
- **Language model time limit:** a model call ends with the error `timeout` after 90 seconds instead of 180. `LAGER_AI_TIMEOUT_SECONDS` changes that; keep it below the response timeout of your proxy.
- **Home-screen install of private instances:** the manifest and icons of an instance that is not public show the app's name, description and icon only to a viewer with access; anyone else gets a manifest named "Lager" with the placeholder icon. Apps that bring their own `rel="manifest"` link need `crossorigin="use-credentials"` on it to keep their name when installed.
- **Instances for other accounts:** a publisher can create at most 5 instances per day for other accounts, and none for an account that already owns half of the instances it may own; an administrator is not limited.
- **Deleting accounts:** the administration area (Users) now offers "Delete account" for a disabled account, with its apps and instances handed to another account or moved to the trash. The account's private data in other people's instances is removed in the background afterwards. Nothing happens to existing accounts on its own.
- **Reserved names:** new apps and instances cannot be named `login`, `account`, `accounts`, `mail`, `smtp`, `ftp`, `assets`, `cdn`, `status`, `support` or `security`, nor like the platform's own host under the apps domain. Existing ones keep working.
- **Custom domains:** a parent domain of the platform host or of the apps domain (`example.com` for a platform at `lager.example.com`) and a name under the platform host (`notes.lager.example.com`) can no longer be attached to an instance. Domains that are already attached keep working.
- **OAuth redirect addresses:** a connecting assistant may register only `https://` addresses, `http://` on this computer, schemes in reverse-domain form with three parts (`com.example.app:`) and `cursor:`. Clients registered with another scheme keep their row but new ones are refused.
- **Unused OAuth clients are removed:** a registered client that holds no sign-in and was last used more than 90 days ago is deleted; the assistant registers again when you next connect.
- **Title and note:** a new app title takes at most 100 characters and a version note at most 500, one line each.
- **Plain http:** a platform that is reached without https on another address than this machine logs a warning at the start, and a request that carries two session cookies is signed out, because without https an app could have planted one of them.
