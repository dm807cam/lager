# 0017. Data from outside comes in through append-only endpoints with a quota of their own

- Status: Proposed
- Date: 2026-11-20

## Context

0007 says that anonymous visitors never write, and instance endpoints answer only the instance's own page with the visitor's session. That keeps instances safe, but it rules out two kinds of app. A public page cannot take one small input from a guest (an RSVP, a guestbook entry, a vote) without making the guest create an account. And nothing outside the instance can feed it: not a counting snippet on the owner's blog, not a form on their website, a webhook, a script, a phone shortcut or a sensor. Such apps needed a second server next to Lager that collected the data, with its own hosting, secret and backup. The workarounds people reach for instead are worse than a narrow door: an API token with full deploy rights in a script, or accounts handed out so that strangers reach contributor level.

Whatever opens here is reachable by anyone on the internet, on a server that is often a Raspberry Pi. It must not become a way to read data, to act as a signed-in visitor, to fill the instance's storage or to keep the server busy.

## Decision

An app can let data in from outside in two ways. Both only **append**: the server makes up the id of every document, so nothing that exists can be read, overwritten or deleted through them.

- **Ingest endpoints.** The `ingest` capability declares up to 8 named endpoints. `POST /_ingest/<name>` on the instance's host stores one JSON object in the endpoint's collection and answers `202` without a body. Who may send is part of the declaration: with `auth: "none"`, browsers on the listed origins (checked against the `Origin` header, with CORS answered for those origins only, and `*` refused); with `auth: "token"`, whoever presents the endpoint's token. A field Lager does not know fails the deploy, and a stored declaration that does not parse opens nothing.
- **`write: "anyone"` in the data rules.** Every visitor who can open the instance, signed in or not, may `add` documents below such a path. Nothing else changes there: `set`, `update`, `delete` and `acquire` stay with the default write level, and the private areas never take such documents. This amends the sentence in 0007: anonymous visitors never write, except that they append where a rule says so.

What keeps this contained:

- **No session.** The endpoint route is mounted before the instance's session is read and never looks at a cookie. A request is anonymous there, whoever's browser sent it, so a page on another site cannot borrow a signed-in visitor's rights (no request forgery), and no document is stored under anybody's name. CORS never allows credentials.
- **Tokens are derived, not stored.** A token is an HMAC of the server secret, the instance, the endpoint and a counter. It can be shown again on the instance page at any time, the platform database alone does not reveal it, and replacing it is incrementing the counter. It opens one endpoint of one instance and nothing else. A presented token is checked before anything else about the sender: wrong tokens slow down the address they come from, but never keep out the right token from the same address, which senders often share.
- **A file and a quota of its own.** Documents from outside are kept in a second database file per instance, `inbox.sqlite`, attached to the same connection as the instance's data. Reads go through a view over both, so to the app they are documents like any other: `db`, queries, live updates and exports cover them. Their quota (`LAGER_INGEST_QUOTA_MB`, default 10 MiB per instance, `0` = off for the whole server) is checked against the pages that file really holds, inside the transaction that adds a document; a write that would exceed it is undone. Nothing in the inbox shares a page with the instance's own documents, and the instance's storage is measured as before, on its own file. So whatever is sent from outside, in whatever sizes and order, cannot fill or fragment the instance's storage, and a full instance does not close an endpoint. Within the inbox the documents of one collection lie next to each other in the order they came in, so dropping the oldest frees whole pages whatever other collections hold.
- **A received document stays one.** Whoever may write the path can change and delete it, but it stays in the inbox: it counts against the ingest quota until it is deleted, and a change that would grow the inbox beyond the quota is refused. When the quota is full, an endpoint refuses (`507`), or, with `onFull: "rotate"`, drops the oldest received documents of its collection. An app that keeps data for long copies what came in into documents of its own.
- **Limits before work.** Per minute an instance takes 150 requests from one client address without a token, 600 per endpoint or rule and 1200 in all, and an endpoint takes a declared number of documents per day (default 10000). They are checked before the body is read; a body is at most `maxBytes` (default 4 KiB, at most 64 KiB) and is not decompressed. The inbox runs with `synchronous = NORMAL`, so requests from strangers do not turn into one disk sync each (the instance's own database keeps the default); live queries hear of received documents at most every 2 seconds per collection, also when rotation drops many at once. Counters of accepted, refused and limited requests are kept in memory, so a refused request never costs a write.
- **Private by default.** Where no declared rule sets `read` for the collection of an endpoint or for a path above it, the server adds one that keeps it to `admin`: what strangers send is not shown to other strangers because a rule was forgotten. Where the app has such a rule, it stands as written, so the default only ever closes what would otherwise be open to every viewer.
- **`anyone` changes one answer.** It decides who may append. Who may write, change and delete on such a path is decided as if the rule were not there, by the next broader rule or the default, so "guests add, only managers change" can be said. The rules engine answers every question it answered before exactly as before.
- **Nothing about the sender is stored.** No address, user agent or origin. `visitor: "daily"` adds a hash keyed with a random value that exists only in memory and is replaced every day, so unique visitors can be counted without cookies and the value cannot be linked across days or traced back, even with the server's secret and database. `country: true` adds the two letters of a header the operator names (`LAGER_COUNTRY_HEADER`), and nothing without that setting.
- **The owner decides.** An endpoint is on from the start only on an instance whose owner also owns or maintains the app: they deployed the declaration themselves (the same line 0016 draws for who is asked before a sign-in). On anybody else's instance it stays off, through every later deploy, until someone who manages that instance switches it on. And as with data rules, only the owner can activate a version whose endpoints differ from the active one.
- **Switches.** The people who manage an instance see every endpoint on its page, with its address, token and counters, and can close each one at once. An administrator can disable the instance; the operator can turn the whole feature off.

Alternatives that lost:

- *Received documents in the instance's own database, counted by an estimate of the pages each one takes,* with the sum taken off what the instance's storage is measured by. This was built first: it keeps one file, and snapshots cover received documents for free. A review showed that no estimate per document holds: rows of one collection deleted from between rows of another leave pages a third full, so data from outside could take almost as much again from the instance's own quota as was counted for it, and the instance's own documents written in between were spread over those pages too. A wall has to be measured, and measuring needs the data to lie apart.
- *Moving a received document into the instance's own database when somebody changes it.* It reads well ("approved, so it is ours"), but it is a move between two files, which SQLite commits one after the other: a crash in between leaves the document in both or in neither.
- *Received documents in snapshots.* It would take a second file per snapshot and a restore that rolls back what guests sent since. A restore is for the instance's own state; received documents are append-only from outside, and exports and backups hold them.
- *Always answering `202`,* as first proposed, so that a prober learns nothing. Senders need the difference: a webhook retries on `429` and `5xx`, and a person with a mistyped token in a phone shortcut needs `401`, not silence. The statuses reveal only what the sender already knows or the instance page of a public address would show; a switched-off endpoint answers like a missing one.
- *Endpoints that are on wherever a version declares them,* as first built. A deploy can already change what an instance does for its visitors, but a publisher opening a way in for strangers on an instance that belongs to someone else is a different thing from changing the page they chose to run. *Off everywhere until switched on* would cost the common case, an owner deploying their own app, a step for nothing.
- *A generic tracker script served by Lager, a retention time per endpoint, origins set per instance.* Left out: the first is app code, the second is what `rotate` and the quota already bound, and the third waits for a need.
- *Stored tokens (hashed, as API tokens are).* A hash cannot be shown again, and the instance page is where people look for the value they pasted into a device a year ago.

## Consequences

- Apps for page views, forms, webhooks, sensors, RSVPs and polls need no second server. `examples/pageviews.html` shows the first.
- An endpoint without a token is open to anyone who can run a script; the origin list keeps other websites out, not people. The guide, `check_app` and the deploy warning say so, and tell assistants to treat what arrives as untrusted input.
- "Anonymous visitors never write" is no longer an invariant of the server but the default. Code that reasons about who can create documents must consider `appendRule` and the ingest route; code that needs the rules of a version must take them from `effectiveRules`, which adds the default for endpoint collections.
- An instance has two database files. Code in the store that reads documents goes through the view `all_docs`; code that writes must say which file it means, and a document never moves between them. An instance can take up to `LAGER_INGEST_QUOTA_MB` on disk beyond its quota, plus 24 KiB for the empty inbox. `usage` of an instance is its own file, as before; `ingestUsage` reports the inbox, in whole pages.
- Snapshots and restores do not cover received documents; exports and the backup command do. A deploy that mishandles received documents is not undone by restoring the snapshot taken before it.
- The ingest quota is shared by all endpoints and `anyone` rules of an instance: one of them filled to the brim leaves no room for the others until someone deletes.
- Changing `LAGER_SECRET` replaces every ingest token, as it ends every session.
- The request limits, the daily counts and the visitor key live in memory: they start again with the server, and several Lager processes would not share them (0002).
- When trust levels for publishing arrive (#7), `auth: "none"` endpoints and `anyone` rules are the natural things to hold to them on servers with open registration. Today only administrators and publishers can deploy, so only they can declare either.
